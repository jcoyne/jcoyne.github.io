cloud-tiles is a deep-zoom viewer for JPEG 2000 that runs entirely in the browser. It reads one JP2 file from any static host using HTTP range requests. There's no IIIF image server involved. The picture is a wavelet decomposition, which is what makes this possible. We'll come back to it.
background

Cloud-Optimized GeoTIFF

1 read the header  ·  2 request only the tiles on screen

Background. Last work cycle Nick and I replaced GeoServer with Cloud-Optimized GeoTIFFs. A COG is an ordinary GeoTIFF laid out so a client can read it in pieces. The header (the IFDs) comes first and says where every internal tile and every lower-resolution overview sits. The client reads the header once, then sends one HTTP Range request per map tile. Any static host works: S3, a CDN.
the question

That sounds like an image server

JPEG 2000 already has multiple resolutions and spatial chunks.

Then it clicked: "read this region at this size and return pixels" is exactly what our IIIF image server does. COG gets that from a static file and a smart client. Could a JP2 work the same way? JPEG 2000 already has both things you need: resolutions are built into the wavelet transform, and the image can be split spatially into tiles or precincts. The missing piece is a decoder that runs in the browser.

Separately, I'd been looking at JPEG 2000 encoders, because OpenJPEG has recently been marked as not supported. That's how I found frames-sg/j2k: a JPEG 2000 and HTJ2K codec written in pure Rust, with unsafe code forbidden. Pure Rust with no C dependencies compiles straight to wasm32-unknown-unknown. We build with wasm-bindgen and SIMD, and each Web Worker gets its own instance. The whole binding layer is about 130 lines: pass in a codestream, the number of resolution levels to drop, and a region, and you get RGBA back. The catch: it needs a complete, valid codestream. So the real work happens in TypeScript, building one from a handful of byte ranges.
jpeg 2000 background

How an image is encoded

Lower resolutions are free: stop decoding early.

A quick tour of how JPEG 2000 encodes an image. First a colour transform from RGB to luma and chroma: the irreversible ICT for lossy, the reversible RCT for lossless. Then the wavelet. The 9/7 filter is lossy, 5/3 is reversible. Each level splits the image into a half-size low-pass band, LL, plus three detail bands. Five levels gives six resolutions, so you can get a smaller version of the image just by decoding fewer levels. The coefficients are quantized and cut into code-blocks, typically 64 by 64, and each block is coded one bit-plane at a time. Classic JPEG 2000 uses EBCOT with an MQ arithmetic coder. HTJ2K swaps in a much faster block coder, which matters in a browser. Two more groupings matter for us. Precincts group code-blocks by position within a resolution, which is how we fetch a region. Layers slice the bit-planes for progressive quality. The unit on disk is the packet: one layer of one precinct of one component at one resolution. Each packet has a header (which blocks are included, zero bit-planes, byte lengths) and a body.

The layout of a .jp2 file

TLM locates every tile-part. PLT gives every packet's length.

On disk, a .jp2 is a sequence of boxes: the signature box, the file type, a header box with image size and colour, and then jp2c, the codestream itself. JPH files for HTJ2K have the same layout. The codestream is a sequence of markers. SOC starts it. SIZ gives image and tile sizes. COD gives decomposition levels, progression order and precinct sizes. QCD gives quantization. Two optional markers matter most to us, and they're highlighted. TLM, in the main header, is a table of where every tile-part starts. PLT, in a tile-part header, lists the byte length of every packet. Each tile-part is SOT, optionally PLT, then SOD, then the packets. In RPCL order the lowest-resolution packets come first, so the thumbnail is a short prefix of the file. Example: Stanford's archive JP2s, written by Kakadu 7.1, are a single tile, RPCL, 7 layers, 5 levels, with PLT and no TLM. For a 4.5 MB file, the first ~42 KB tells us where every packet is.
complications

Every JP2 is laid out differently

Here's where it gets hairy: real-world JP2s are encoded in every possible way. Tiled? Then is there a TLM marker? If so, the main header tells us where every tile-part is. If not, we walk the SOT markers, one small read per tile-part. Are the tile-parts split by resolution, Kakadu's ORGtparts=R? Then we can skip the high-resolution parts entirely. Untiled? Then everything depends on PLT. Without it you have one giant tile and must download the whole file. With it, we build a packet index and check the count against what the geometry predicts. If they disagree, we fall back rather than decode garbage. On top of that, the progression order (LRCP, RLCP, RPCL, PCRL, CPRL) decides where a region's packets sit. RPCL keeps resolutions together; LRCP scatters a region's packets across the whole file. Precinct sizes can differ per resolution, and COC overrides them per component. The geometry code implements the spec's Annex B formulas to track all of this.
two strategies

Fetch by tile, or by precinct

Tiled + TLM: fetch those tiles and rewrite SIZ so they form a small image.

Untiled + PLT: keep the view's packets and swap the rest for empty ones.

So there are two strategies. For tiled files with TLM: work out which tiles the view overlaps and fetch only those tile-parts, and only up to the resolution we need when the parts are split that way. Then rewrite SIZ so the decoder thinks it's a small image made of just those tiles, renumbered. If we drop resolution levels, we trim COD and QCD as well. For untiled files with PLT there's only one tile, so we can't drop tiles. Instead we keep the full packet sequence but replace every packet outside the view with a single zero byte, which is a legal empty packet. We keep a 16-sample margin because the wavelet filters reach into neighbouring samples. This works on Stanford's existing archive files. Either way the decoder gets a valid codestream. The tests check that both paths are bit-exact against decoding the whole file, and within ±1 of Kakadu.
putting it together

How a tile is drawn

Here's what happens for each tile. OpenSeadragon asks for a tile by level, x and y. The tile source turns that into how many resolution levels to drop (maxLevel minus level) and a pixel region at that resolution. Jp2Image.plan returns the byte ranges it needs, plus a function that builds the codestream. HttpRangeSource fetches the ranges. It merges nearby ones into a single request, caps concurrency, and keeps an LRU cache, so the low-resolution data every tile needs is fetched only once. Then we build the small codestream and send it to a worker. The worker runs the WASM decoder and hands back an ImageBitmap without a copy, and OpenSeadragon draws it. If you pan away, queued decodes are cancelled. Fetches aren't, because another tile probably needs the same bytes.

So, do we still need an image server? For viewing, not necessarily. Opening an image takes three to five requests, 90 to 275 KB in our samples. The first view fetches 15 to 30 percent of the file. A tile decodes in 65 to 85 milliseconds in the browser. The output is within one of Kakadu, and bit-exact against decoding the whole file. What we gain: any static host with Range and CORS, no server CPU, and the original codestream rather than a second lossy generation. What we give up: region URLs, thumbnails and crops on demand, size limits such as maxWidth, and access control by size or region. It also needs a modern browser. Other IIIF viewers don't know about it, but a manifest can advertise both, and they fall back to the Image API. The one request for our encoding pipeline: turn on PLT (ORGgen_plt=yes). Without it the viewer has to download the whole file. The viewer is live, and the samples menu includes a 1.2 GB piano roll straight from stacks. Questions?
